# v0.7 Implementation Plan — 沉浸感 + 长线持续

> Use superpowers:subagent-driven-development.

**Theme:** Less engineering plumbing, more "actually fun while playing". Four gameplay features (journal, XP, BGM, portraits) balanced with two perf items (summary recursion, model warmup).

**Why this mix:**
- v0.5 / v0.6 finished the durability / packaging / mobile baseline
- The tooling is now stable enough that we should move "up the stack" toward what makes a TRPG session memorable: progression, atmosphere, visualizing your world
- But two perf items go in to keep long sessions playable: recursive summary compression (no more context overflow at hour 3) and model warmup (no more 5-10s wait on the very first turn)

## Phase B — sequential (gameplay state)

### Task B2: Character XP + level system

**Files:**
- Modify: `backend/src/dzmm/db/models.py` (Character.xp, Character.level columns)
- Modify: `backend/src/dzmm/service/state_apply.py` (handle `<character_xp>` tag)
- Modify: `backend/src/dzmm/prompts/gm_template.py` (mention `<character_xp>` in format)
- Modify: `backend/src/dzmm/api/routes_characters.py` (add `POST /characters/{id}/levelup` taking `{stat: 'hp'|'sanity'|...}`)
- Modify: `backend/tests/test_state_apply.py`
- Modify: `backend/tests/test_api.py`
- Modify: `frontend/src/views/GameView.vue` (XP bar in header, level-up dialog when threshold crossed)
- Create: `frontend/src/components/LevelUpDialog.vue`

**Goal:** GM can award XP via `<character_xp delta="50">解决了卫兵的盘问</character_xp>`. When current XP crosses level threshold (level 1 → 2 at 100, 2 → 3 at 250, 3 → 4 at 500, etc), frontend pops a dialog letting the player pick which base stat to increment by 1 (or +5 if HP/stamina). Level becomes part of character card injected into next prompt so GM knows the PC has grown.

XP formula: `xp_to_next_level(n) = 100 * n * (n+1) / 2` (n=1: 100, n=2: 300, n=3: 600).

- [ ] Schema migration adds `xp INT DEFAULT 0`, `level INT DEFAULT 1` columns.
- [ ] `<character_xp>` tag handled in state_apply (similar to npc_update); tests cover positive delta and threshold crossing.
- [ ] gm_template adds the tag to behavior section: "完成关键任务、克服重大挑战、大成功的判定时给 XP（典型 10-50）"; injected character card includes current level.
- [ ] Frontend XP bar in GameView header showing current/threshold; when threshold crossed locally (after applying tag), pop LevelUpDialog asking which stat.
- [ ] Backend `POST /characters/{id}/levelup` body: `{stat: string, amount: number}`. Updates `base_stats_json`. Also auto-syncs CharState if session is active.

### Task B5: Recursive summary compression

**Files:**
- Modify: `backend/src/dzmm/service/summarizer.py`
- Modify: `backend/src/dzmm/db/models.py` (add `Timeline` table)
- Modify: `backend/tests/test_summarizer.py`

**Goal:** When summary itself exceeds 1500 tokens, run a "compress-only" call that:
1. Extracts key events from old summary into a `timeline` table (importance ≥ 2 events become permanent records)
2. Rewrites summary down to ~600 tokens
3. timeline rows are NOT injected into subsequent prompts (they're for retrieval if user asks "did I meet that NPC last week?" — frontend can show a separate Timeline view, OR backend search exposes them via /sessions/{id}/timeline)

For v0.7, just persist timeline; surfacing UI is v0.8.

- [ ] Summarizer's existing trigger expanded: if existing summary > SUMMARY_SOFT_LIMIT (1500), call a separate compression prompt.
- [ ] New `Timeline` table: `(id, session_id, turn, event_text, importance)`. Compression prompt asked to output `<event importance="N">text</event>` blocks alongside the new summary; backend parses both into respective tables.
- [ ] Test: after seeding 30+ messages with diverse content, run compression; assert new summary < SOFT_LIMIT and timeline has ≥2 rows.

## Phase C — model warmup

### Task C6: Pre-warm GM model on session open

**Files:**
- Modify: `backend/src/dzmm/api/routes_sessions.py` (extend GET /sessions/{id} to optionally trigger warmup; or add POST /sessions/{id}/warmup)
- Modify: `frontend/src/views/GameView.vue` (call warmup in onMounted)

**Goal:** When user enters game page, fire-and-forget a tiny ollama call that loads the model into GPU. By the time they type and click Send, model is hot.

- [ ] New `POST /sessions/{id}/warmup` endpoint that resolves the GM model config, opens a streaming request that asks for 1 token, immediately closes. Returns 202.
- [ ] Test: just verifies the endpoint exists and 202s with a stub client.
- [ ] Frontend: after BootGate ready and sessionsStore.get succeeds, `sessionsApi.warmup(sessionId).catch(()=>{})`. Fire-and-forget so it doesn't block UI.

**Phase ordering:**
- Phase A parallel ×3: A1, A3, C6 (no overlap)
- Phase B sequential: A4 → B2 → B5 (each touches db/models.py)
