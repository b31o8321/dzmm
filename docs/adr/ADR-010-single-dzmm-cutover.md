# ADR-010: 收敛为单一 DZMM 产品并受控替换旧版

**Status:** Proposed  
**Date:** 2026-08-30  
**Deciders:** 产品与维护者

## Context

仓库当前同时存在旧版 `main`（v0.16.0）与独立的 vNext 实现。vNext 已覆盖本地
世界、Run、叙事、规则、模型档案、跨平台 Local Host 和 portable bundle，但仍有
发布证据缺口，且内部仍使用 `dzmm_vnext`、`DZMM Next`、`.dzmm-vnext-v3` 等预览名。
两条长期产品线会造成用户误装、功能分叉、数据边界不清和维护成本翻倍。

## Decision

将 vNext 作为旧版的替换候选，最终产品名统一为 **DZMM**；不长期维护“DZMM Next”
作为第二产品线。切换采用可回滚的分阶段方式：

1. 先完成 P0 玩家闭环和三端发布 gate，并明确数据迁移/不迁移策略。
2. 从当前 vNext 建立干净的 cutover 分支，统一用户可见名称、包名展示和默认数据目录。
3. 将旧版代码从默认构建与发布路径移除；保留旧版 tag/归档分支用于回滚，不再作为日常产品。
4. 只有完成导出/导入或明确的旧存档不迁移提示后，才删除旧版实现文件；删除前保留
   可审计的迁移说明和版本化归档。

### Migration policy for the first cutover

首个替换版本采用**不自动迁移旧版数据库**：旧版 `~/.dzmm/dzmm.db` 与当前隔离的
`~/.dzmm-vnext-v3/dzmm-next.db` 不在启动时复制、覆盖或合并。原因是两者的领域模型、
表结构和回合语义不同，静默转换无法保证世界、旅程和历史的一致性。应用会明确告知玩家
这一点；需要带入内容时，只能由玩家主动导出/导入世界包或旅程快照，源数据保持不变。

该策略不等于放弃回滚：旧版通过版本化 tag/归档分支保留，vNext 数据目录在 cutover 后
仍可独立读取。后续若要提供批量迁移，必须另立版本化迁移工具和逐项验收，不作为首个
替换版本的隐含行为。

## Options Considered

### Option A: 长期维护两条产品线

| 维度 | 评估 |
|---|---|
| 用户理解 | 差，容易误装或误以为数据互通 |
| 维护成本 | 高，功能和修复需要双写 |
| 回滚 | 简单 |
| 结论 | 不采用 |

### Option B: 立即删除旧版并把 vNext 直接合并到 main

| 维度 | 评估 |
|---|---|
| 用户理解 | 好 |
| 维护成本 | 低 |
| 发布风险 | 高；当前仍有跨平台安装与可见窗口证据缺口 |
| 结论 | 当前不采用，待 gate 通过后执行 |

### Option C: 受控 cutover（采用）

先以 vNext 通过玩家体验和发布 gate，再统一命名、建立迁移边界、归档旧版并删除旧版
默认路径。旧版只保留版本化回滚资产。

## Cutover Gates

- [ ] 新世界创建 → 开场 → 10–30 回合 → 正式结局 → 返回 World → 同 World 新 Run。
- [ ] 叙事/对话/NPC 主动事件与规则状态因果可理解；同世界重玩存在 Run 级变化。
- [ ] 模型设置 CRUD、默认模型、Probe、加载/超时/取消/失败恢复在桌面和 Android 对齐。
- [ ] 历史内容可阅读、当前操作区固定、状态/事件独立呈现，长局不丢历史。
- [ ] macOS 安装包有可见 WebView 窗口并完成主路径；当前 sidecar/API 闭环已通过，但 GUI 点击验收仍待完成。
- [ ] Windows 原生 installer 完成安装后主路径；当前 NSIS/sidecar 构建与 smoke 已通过，安装后 GUI 仍待完成。
- [x] Android release APK 在本地模拟器完成冷启动、创建、游玩、正式结束、重开恢复；phase157/158 已在
      `emulator-5554` 完成新世界→10 回合→正式隐藏结局→同世界新 Run，并在 force-stop 后恢复；真机可作为
      独立发布证据，不阻塞本地开发，但不能被伪称为已验收。
- [x] 旧版存档有明确的“不自动迁移”说明，并提供玩家主动导出/导入世界包或旅程快照的路径。
- [~] 旧版归档 tag 已建立（`dzmm-legacy-v0.16.0-2026-08-30`）；cutover 回滚步骤和发布前恢复演练仍待完成。
- [ ] CI、测试、构建和发布脚本只引用统一产品名与新默认路径；用户可见名称已统一，内部包标识和默认目录迁移仍待 cutover。

## Consequences

- 用户最终只看到一个 DZMM，后续功能不再按“旧版/Next”分叉。
- 需要一次命名、包标识和默认目录迁移；旧数据不能在没有明确策略时静默覆盖。
- 旧版仍可通过 tag/归档分支恢复，但不再接受日常功能开发。
- 在 gates 未通过前，继续保留独立 vNext worktree 和旧版 `main`，避免不可逆删除。
