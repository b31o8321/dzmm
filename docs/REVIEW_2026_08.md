# 项目评估与改进建议（2026-08）

> 基于对 backend / frontend / 功能全景三条线的代码级评审。评分对照竞品
> （AI Dungeon、SillyTavern、RisuAI、NovelAI、Realm）：功能 7.5 / 10，
> 后端 8 / 10，前端 6.5 / 10，综合 7.3 / 10。
> 事实依据均来自当前代码，文中给出具体文件路径，可直接按条目开工。

## 综合结论

dzmm 的核心价值在于「LLM 只负责叙事，规则由 Python 决定」这条架构路线的
完整落地：真随机骰子、技能/战斗/物品结算、事件谓词、`_enforce_dice_outcome`
纠错，都是同类开源产品没有的能力。后端工程素质（分层、测试、事务边界）
明显高于同类；主要欠账集中在前端测试、CI 护栏和少数超长文件。

## 一、缺陷清单与补齐方案

按「收益 / 成本比」排序，P0 最优先。

### P0-1 后端 CI 缺失：验证纪律靠自觉

**现状**：`.github/workflows/` 只有 `e2e.yml` 和 `release.yml`，没有跑
pytest 和 ruff 的 workflow。AGENTS.md 要求的「交付前全量 pytest + ruff」
没有任何强制手段，一旦回归只能靠人肉发现。

**补齐方案**：新增 `.github/workflows/backend-ci.yml`，成本约 30 分钟：

```yaml
name: backend-ci
on:
  push: { branches: [main] }
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.11", cache: pip }
      - run: pip install -e ".[dev]"   # 按实际 extras 名调整
      - run: python -m ruff check src tests
      - run: python -m pytest -q
```

验证标准：故意提交一个会让测试失败的改动，CI 必须变红。

### P0-2 前端测试近乎为零

**现状**：`frontend/tests/` 全目录仅 1 个 14 行的 `api.test.ts`，且只断言
「函数存在」（`expect.any(Function)`），测试价值接近零；e2e 仅 1 条
`e2e/smoke.spec.ts`。而前端风险最高的部分恰恰是 SSE 回合状态机、会话切换
状态恢复、协议降级补救——全部零覆盖。`@vue/test-utils` 已安装未使用。

**补齐方案**（分三步，每步独立可交付）：

1. **删掉无实效的单测，补 composables 单测**。优先级：
   - `useTurnStream.ts`：喂它构造的 SSE 行序列（含 CRLF、跨 chunk 撕裂的
     `event:`/`data:`、半行残留 buffer flush），断言解析结果。这是纯函数
     级测试，最便宜且覆盖最高风险。
   - `useGameTurn.ts` 的 `cleanNarrative` / `extractChoices` 降级逻辑：对
     LLM 协议违规输出（unclosed tag、缺 choices 块）逐 case 断言。
   - 工具：Vitest 已配置，直接写即可。
2. **扩 e2e**：复用 `e2e/mock_backend.py` 的 stub LLM，新增 3 条场景——
   完整回合（叙事→骰子→状态面板更新→choices 可点）、会话切换/刷新后
   状态恢复、回合中刷新页面不产生脏数据。
3. **组件测试（可选）**：`StatePanel.vue`、`MessageList` 的渲染快照 +
   关键交互，用 `@vue/test-utils`。

验证标准：`npx playwright test` 至少 4 条场景全绿；composables 单测进入
`npm test` 且覆盖撕裂 chunk 用例。

### P0-3 AbortSignal 形同虚设，流式回合存在泄漏/错写风险

**现状**：`streamTurn` / `npcTick` 均接受 `AbortSignal` 形参，但全项目
grep 无任何 `AbortController` 调用。组件卸载或切换会话时，旧会话的流式
回合不会被取消——响应回来后可能把旧会话的事件写进新会话的 UI，或触发
针对已卸载组件的状态更新。

**补齐方案**：

1. `GameView.vue` 持有一个 `AbortController`，在会话切换（`onMounted`
   恢复逻辑入口）和 `onUnmounted` 时 `controller.abort()`。
2. `useGameTurn` / `useTurnStream` 在 `onDone`/`onTag` 回调入口检查
   `signal.aborted`，提前 return，不派发任何状态变更。
3. `useWizardStream.ts` 同样处理（向导步骤切换时取消上一步流）。

验证标准：e2e 新增用例——回合进行中切换到另一个会话，等待流结束后断言
新会话 UI 未被旧会话内容污染。

### P1-1 SSE 解析逻辑复制了 3 份

**现状**：几乎相同的 line-buffer + `event:`/`data:` 解析循环存在于：
- `frontend/src/composables/useTurnStream.ts:37-52`
- `frontend/src/api/sessions.ts:344-365`（npcTick 内联重复 fetch+reader）
- `frontend/src/composables/useWizardStream.ts:23-51`

修 bug（如之前的 CRLF 归一化）需要改三处，漏一处就是行为分叉。

**补齐方案**：抽 `frontend/src/utils/sseStream.ts`，导出一个
`parseSseStream(reader, onEvent)`（或 async generator），三处改为调用。
顺手把 `api/sessions.ts:413-429` 的 `_dispatchBlock` 一起收编。改动是
纯重构，现有 P0-2 的单测正好当回归网——所以先做 P0-2 再做这条。

### P1-2 GameView.vue 神组件（1420 行）+ 内部逻辑重复

**现状**：`frontend/src/views/GameView.vue` script 887 行，混合回合编排、
历史恢复、NPC initiative 定时器、BGM/TTS、token 统计、建议生成等。其中
`regenerate()` 与 `editPrev()`（528-564 行）几乎逐行重复；583-610 行的
npcTick tag 处理与 `useGameTurn` 的 `onTag` 部分重复。

**补齐方案**（不要一次性大拆，按提取单元渐进）：

1. 先消重：`regenerate`/`editPrev` 合并为一个带模式参数的函数。
2. 把 npcTick 的 tag 处理逻辑下沉进 `useGameTurn`，删掉视图层副本。
3. 逐块提取 composables（每块一个 PR，提取后行为不变）：
   - `useTurnTimers`（initiative 4 秒倒计时横幅）
   - `useGameAudio`（BGM/TTS 编排，或直接并入现有 `useAudio`）
   - `useHistoryRestore`（onMounted 两遍状态应用，见 P1-4）
4. 目标：GameView.vue 降到 500 行以内，只留模板和接线。

### P1-3 game.py 持续膨胀（2452 行）与 apply_tags 大分发链

**现状**：`backend/src/dzmm/service/game.py` 2452 行，新旧 run_turn 双路径
共存（`game.py:644` 起）；`service/state_apply/_impl.py:190-306` 的
`apply_tags` 是约 30 个 `elif` 的大分发链，每加标签都要改这里。

**补齐方案**：

1. 确认旧 run_turn 路径已无调用方后删除（859 个测试是安全网，删前先全绿）。
2. `apply_tags` 改注册表模式：`dict[str, Callable[[TagContext], None]]`，
   每个 `state_apply/` 模块自带 handler 注册，分发链消失，新增标签只需
   新增模块。与现有「每标签一模块」的拆分天然契合。
3. `game.py` 按职责拆：回合编排 / 消息查询 / debug 诊断至少分三块。

### P1-4 会话状态恢复靠手写补丁

**现状**：核心游戏运行时状态不在 Pinia，而在 `useGameState` composable +
GameView 局部；会话切换/刷新恢复只能全量重拉 messages，`GameView.vue:708-792`
onMounted 两遍应用即为补丁痕迹。store（薄 CRUD 包装）与 composable 双轨割裂。

**补齐方案**：把回合运行时状态（当前流、dice、npcTick、stats）收进一个
`useGameSessionStore`（Pinia setup store），恢复逻辑收敛为 store 内的
`restore(sessionId)` 单入口，GameView 只调它。P0-3 的 abort 也顺势放进
store，天然解决跨会话泄漏。这条成本最高，建议在 P1-2 的 composables 提取
完成后再做，避免两次大改。

### P2-1 异常处理收口

61 处 `except Exception`（多数 `# noqa: BLE001` 有意为之），少数静默吞掉：
`turn.py:88-89`（warmup）、`state_apply/_impl.py:445`。补齐方案：逐个过一遍，
真正的「允许失败」改为窄化捕获（如只捕 `httpx.HTTPError`）并加 debug 日志；
ruff 若引入 `BLE` 规则则保留显式 noqa。属于渐进清理，不阻塞发版。

### P2-2 工具链加严（可选）

- 引入 mypy：先 `mypy dzmm.engine dzmm.parsing dzmm.models` 这三个纯逻辑
  包（依赖少、最容易过），service/api 后补。
- ruff 加规则集：`select = ["E", "F", "I", "B", "UP", "BLE"]`，存量违规
  用 `ruff check --fix` 批量消。
- 前端无 codegen，类型手工同步后端 schema（BootGate 的版本 skew 横幅就是
  对这个风险的补丁）。可引入 `openapi-typescript` 从 FastAPI 的
  `/openapi.json` 生成类型，手写层只留业务封装。

### P2-3 Tauri 退出兜底

`frontend/src-tauri/src/lib.rs` 只处理 `WindowEvent::Destroyed`，建议补
`CloseRequested` 分支调用 kill；kill 改为 `kill_on_drop` 或先 SIGTERM/
优雅退出再硬杀；可选：sidecar 崩溃后 watchdog 自动重启（ BootGate 已有
重试 UI，后端侧补自动拉起即可）。

## 二、产品功能缺口（按需排期）

非缺陷，是与竞品对照后的机会项，供 roadmap 参考：

1. **会话/世界导入**：已有 JSON/MD 导出，补导入即形成备份-迁移闭环，也
   是未来「剧本分享」生态的前提。成本最低、收益直接。
2. **规则集可配置**：当前只有一套自创 d20 规则。`engine/` 已是纯函数库，
   把属性/技能表/战斗公式抽成规则集配置（CoC 的 d100 + SAN、5e 的优势
   机制），可显著扩大受众。
3. **图像生成接入**：SD/Flux 本地 sidecar（可参照 CosyVoice 的一键安装
   sidecar 模式）做场景插图和 NPC 头像，是竞品标配。
4. **战斗 UI 交互化**：changelog 已自认半成品——点击 NPC 攻击、点击换装。
5. 上下文目前按 16K 优化，长上下文模型（32K+）未适配；摘要每 10 回合
   35-49s 长尾也可后台化。

## 三、建议的执行顺序

```
第 1 周   P0-1 后端 CI          （半小时，先有安全网）
第 1-2 周 P0-2 前端测试三步走   （先 useTurnStream 单测，再 e2e）
第 2 周   P0-3 AbortController  （配合新 e2e 用例验证）
第 3 周起 P1-1 SSE 解析抽公共模块 → P1-2 GameView 消重 → P1-3 后端拆分
之后      P1-4 状态收进 Pinia；P2 按顺手节奏清理
功能侧    导入功能（P1 级收益）→ 规则集配置 → 图像生成
```

原则：**先建测试安全网，再做重构**。P0-1/P0-2 必须在 P1 系列重构之前完成，
否则每一步重构都在裸奔。
